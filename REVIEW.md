Two behaviours I had read from the code alone are now checked against Python Leo
and are exact parity, so they are not findings:

- `util::xml_escape` (`util.rs:447`) drops characters below 32 other than tab,
  CR and LF. Leo does the same, through
  `entities = {chr(z): '' for z in range(32) ...}` (`leoFileCommands.py:656`).
- Opaque unknown attributes are written unescaped (`leofile.rs:406`, `:439`).
  Leo also writes the hexlified pickle raw (`leoFileCommands.py:1984`). Routing
  both through `util::xml_quoteattr` is a no-op for hex and would harden the
  writer against a value some other tool wrote, but it is not a divergence.

## What the design gets right

1. **The model/view boundary is real, not aspirational.** `leolib` has no
   `leotui` dependency and no display code. `Outline` holds the vnode arena;
   `Document` adds undo and the structural commands. The directive scanners
   (`outline.rs:727-900`) answer per document, not per view, so two views cannot
   disagree about a node's language. The Python `leolib` is a facade over
   `leo/core`, which still holds the Qt-era code; this one is a reimplementation
   with the same public functions.
2. **Clones are modelled as a DAG, not copied subtrees.** Vnodes live in an
   arena and refer to each other by `VnodeId` (`node.rs`), which is the only
   shape that makes Leo's clone semantics correct rather than approximated.
3. **The conformance corpus is the strongest part of the project.** Each case in
   `demo/` has an expected file generated by Python Leo
   (`scripts/make_corpus.py`), and leo-editor checks Python Leo against the same
   files. The two `KNOWN` lists in `tests/corpus.rs:22-32` record deliberate
   divergences and fail the test when an entry stops diverging, so the list
   cannot go stale. Few ports pin their own known-wrong behaviour this way.
4. **`@auto` imports are verified before they are kept**
   (`external.rs:160-207`). An `@auto` file has no sentinels, so a lossy
   importer would overwrite the user's source on the next write. The tree is
   written back and compared with the file; a mismatch puts the whole file in
   the node's body and reports an error. Leo does not do this check.
5. **The overwrite guard** (`outline.rs:550`). An `@<file>` node whose file
   exists but was never read is refused, and `WriteResult::refused` lets a front
   end ask. This closes Leo issue #50.
6. **Writes are atomic and preserve mode** (`external.rs:515-538`): temp file,
   `set_permissions` from the original, rename. Leo writes in place with
   `open(fileName, 'wb')` (`leoFileCommands.py`, `g.writeFile`), so this is
   stricter than the original. Unchanged content is not written at all.
7. **Failure is per file, not per document** (`external.rs:95-124`).
8. **Panics are rare and deliberate.** Excluding test modules, the whole
   workspace has under 40 `unwrap`/`expect`/`panic!`/indexing sites; no
   `unsafe`. The TUI restores the terminal from a panic hook
   (`main.rs:277-283`).
9. **`docs/dev/optimizations.md` records measurements, not intentions**, with
   profile shares, the change that took the load from 779 ms to 99 ms, and the
   two optimizations deliberately not done and why.

## Findings

### 1. A non-UTF-8 external file is silently corrupted on save (high) -- FIXED

Fixed after this review by refusing such files; see the CHANGELOG and
`docs/dev/porting-notes.md`. The finding is kept as written, since it records
what the corpus entries did not say. What follows described `8d7a2d0`.

Reproduced end to end, twice, on `demo/cases/encoding`:

    writecheck enc/encoding.leo --edit names
    written: 1
    name = 'caf\xef\xbf\xbd'      (was 'caf\xe9')
    other = 'na\xef\xbf\xbd\xefve'  (was 'na\xefve')

Python Leo on the same file and the same operation writes back byte-identical
bytes (213 in, 213 out, both high bytes preserved).

The path: `read_file_to_string` decodes with `from_utf8_lossy`
(`external.rs:327-333`), so every high byte becomes U+FFFD. `file_contents`
computes the node's effective encoding and passes it to `replace_file`, which
takes it as `_encoding` and ignores it (`external.rs:515`). Everything is
written as UTF-8.

Leo reads with the encoding from the BOM or the `-encoding=` field of the
`@+leo` sentinel header (`leoAtFile.py:1085-1111`) and writes back with that
same encoding (`leoAtFile.py:3147`, `:3191`).

Three things make this worse than the pinned corpus entry suggests:

- The read reports success. `ReadResult.read` is 1 and `errors` is empty, so a
  front end has nothing to warn about.
- The write reports success. The file is listed in `WriteResult.written`.
- It is reachable from the shipping TUI. `app.rs:517` writes with
  `dirty_only = true`, and editing any node in the tree marks the `@file` root
  dirty. One edit plus one save destroys the file's non-ASCII characters.

`tests/corpus.rs` pins this under `KNOWN` and `KNOWN_TANGLE`, but both entries
describe it as a *read* divergence ("external files are decoded as UTF-8
whatever their `@encoding`"). The damage is on the write.

Cheapest fix, short of adding a decoder: when a node's effective encoding is not
UTF-8, or when the decode replaced any byte, treat the file as unread. The
existing `may_overwrite` machinery then refuses the write and the front end
reports it, which turns silent corruption into a visible refusal. Full fix:
`encoding_rs`, one dependency, for the encodings `@encoding` accepts.

Taken: the refusal, with no new dependency. Three paths bypass the read guard
and needed their own -- `@nosent` is never read, `@clean` is exempt from
`may_overwrite`, and a front end can approve an overwrite -- so the guard sits
in four places, and such a file is no longer offered for approval. Both corpus
entries changed: `KNOWN` now records a refusal, and `KNOWN_TANGLE` is empty,
because a file the read refused is no longer tangled at all. Editing latin-1
outlines remains something Leo does and this port does not; revisit if anyone
asks for it.

The `.leo` reader had the same lossy decode (`leofile.rs:161`), which this
review noted but did not raise as a finding. It is fixed the same way: a `.leo`
file that is not UTF-8 now fails to open rather than opening with U+FFFD in its
headlines.

### 2. The importer harness finds a Python Leo bug, and nothing records it (low, upstream)

Digest comparison over 591 Python files from the leo-editor checkout: 579
identical, 12 differing. In all 12, Python Leo raises and leo-rs produces a
tree. All 12 files are zero bytes, and the traceback is the same:

    File "leo/core/leoAtFile.py", line 642, in readFileAtPosition
      if p.v.gnx != old_gnx:
    AttributeError: 'NoneType' object has no attribute 'v'

So `@auto` on an empty file crashes Python Leo at `b6e06060ad`, and leo-rs
handles it. This is worth reporting upstream, and worth a corpus case here so
the difference is pinned rather than rediscovered.

It also means the README's `@auto` table ("998 of 1,000 identical; the 2
differences are a deliberate fix") cannot be reproduced on the current checkout
without excluding empty files. The table should say which leo-editor commit it
was measured at, as `docs/dev/comparison.md` already does.

### 3. Traversal cost is quadratic in outline depth (medium)

`Position` carries a stack of its ancestors, so `self_and_parents` allocates
O(depth) positions each carrying an O(depth) stack. `get_path` calls it per node
(`outline.rs:727`), `full_path` calls `get_path`, and `find_files_to_read` calls
`full_path` per node.

Measured, release build, a single chain of N nodes through `examples/writecheck`:

| depth | time |
|---|---|
| 500 | 0.06 s |
| 1,000 | 0.64 s |
| 2,000 | 7.05 s |
| 20,000 | over 300 s, killed |

Reading alone (`examples/dump`, no `full_path`) handles 20,000 in milliseconds,
which locates the cost in the path scanners, not the XML reader.

Real outlines are shallow: `LeoPyRef.leo` is 11,581 nodes at depth ~10 and loads
in 99 ms. This is a bound worth recording, not work to schedule. If it is ever
fixed, memoizing `get_path` per vnode for the life of one read is the smaller
change; sharing `Position` stacks is the larger one.

Same shape, smaller: `Outline::scan_from` (`outline.rs:699`) rebuilds
`all_positions()` on every call, so `goto-next-marked` is a full traversal per
keystroke.

### 4. Three error conventions in one public API (medium)

`leolib` returns `Box<dyn Error>` (`lib.rs:87`, `document.rs:37`), `String`
(`external.rs`, `atfile_write.rs`, `document.rs:373`) and `LeoFileError`
(`leofile.rs:32`). A caller cannot tell "file missing" from "importer failed"
from "not a .leo file" without matching on message text. For a crate published
on crates.io this is the API decision hardest to revisit later, and
`docs/dev/comparison.md` names a stable `leolib` API as the next work under two
of its three readings of what the project is for.

One `leolib::Error` enum, with the existing `LeoFileError` variants plus `Io`,
`NotReadable`, `ImportFailed` and `RefusedOverwrite`, is a contained change at
0.2.

Related: `lib.rs:15-29` makes every module public, so the whole internal surface
is semver-visible. Consider `pub(crate)` for `seqmatch`, `atfile_read`,
`atfile_write`, `atclean` and `langdata`, re-exporting only what callers need.

### 5. No CI (medium, process)

There is no `.github/workflows`. `make check` exists and passes, but nothing
runs it on push, and `make corpus` -- which I had to run by hand to confirm the
expected files still match Python Leo -- needs an external checkout. For a crate
that publishes to crates.io, a workflow running `make check` on push plus
`cargo audit` on a schedule is the minimum. The corpus check can run in CI
against a pinned leo-editor commit; the same pin fixes finding 2's reproducibility.

### 6. Memory grows monotonically within a session (low)

By design, deleting a node never frees its vnode (`undo.rs:8-9`), which is what
makes undo a relink. The undo stack is also uncapped (`undo.rs:106`). Neither
matters for an editing session of ordinary length; both mean a long-lived
process editing a large outline has no steady state. If a cap is ever added, it
must drop beads and their vnodes together.

### 7. A `.leo` file is executable-grade input (documentation gap)

`full_path` resolves `@path` and `@<file>` names absolutely
(`util.rs:387-401`): an absolute path wins, `~` expands, `..` traverses.
Writing creates missing directories (`external.rs:523`). Opening an untrusted
`.leo` file and writing all can create files anywhere the user can write.
`may_overwrite` blocks clobbering an existing unread file, not creating a new
one.

Leo behaves the same way, so this is not a defect to fix. It belongs in the
README beside the other porting notes: a `.leo` file from an untrusted source is
as dangerous as a Makefile from one.

### 8. `app.rs` is the one structural outlier (low)

2,542 lines, with 59 methods on a single `App` impl spanning lines 197-1526.
Everything else in the workspace is factored into modules under 1,100 lines,
including the parts of the TUI that were extracted (`editor/`, `minibuffer`,
`search`, `substitute`, `theme`). The dispatcher, the mode handlers, the
minibuffer glue and the command-line runner are four separable concerns already
visible in the method names.

## Test coverage

333 tests, with the split in the right place: the model's risky paths are
covered by integration tests that go through disk (`round_trip.rs`, 17 tests,
including refusal, mode preservation, failed reads and `import_at_file`), and
the corpus tests check against Python Leo's own answers.

Source files with no unit tests: `external.rs`, `langdata.rs`,
`importers/lines.rs`, `importers/python.rs`, `importers/rust_lang.rs`.
`external.rs` is covered well by `round_trip.rs`, so only the three importer
modules are genuinely untested in isolation. They are exercised through the
`auto_languages` corpus case and, when someone runs it by hand, the 591-file
differential above -- weaker evidence than a per-importer test of the edge cases
each language has.
